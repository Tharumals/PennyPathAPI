# Architecture Guidelines

This project is a **modular monolith**: one deployable Node.js application, split internally into isolated domain modules. Each module owns its data and exposes a small, explicit public contract.

**Read this file before:** creating a module, calling one module from another, adding an event, adding a table, or changing the project structure.

Related docs: `docs/api-conventions.md` (HTTP rules), `docs/database.md`, `docs/authentication.md`

## Why this architecture

- One deployment and one database keep operations simple
- Strict module boundaries keep the code easy to reason about and let teams work independently
- Any module can later be extracted into a separate service with minimal changes

These benefits only hold if the boundaries are respected. **Treat a boundary violation as a bug, and let CI catch it.**

## Design Principles

1. **Boundaries over layers.** Modules are split by business capability (payments, ledger, notifications), not by technical type.
2. **Contracts over internals.** Modules depend on each other's published contracts, never their implementation.
3. **Own your data.** One module owns each table. Nobody else reads or writes it.
4. **Explicit wiring.** Dependencies are passed in (composition root), not reached for through global singletons.
5. **Eventual consistency between modules, strong consistency inside one.**
6. **Enforce by tooling, not by convention.** Rules that are not checked in CI will be broken.
7. **Stay simple.** Start with few modules and split only when there is a real reason (section "Choosing Module Boundaries").

## Project Structure

```
src/
  app.ts                    # Builds the Express app, wires modules, mounts routers, error handler
  server.ts                 # Entry point (starts the HTTP server, graceful shutdown)
  config/
    env.ts                  # Parses and validates environment variables (Zod)
  db/
    index.ts                # Drizzle client and transaction helper (see docs/database.md)
    migrations/             # Generated by drizzle-kit, never hand-edited
  modules/
    payments/
      index.ts              # PUBLIC entry point: the only file other modules may import
      payments.module.ts    # Composition: createPaymentsModule(deps) wires internals
      contracts/            # PUBLIC types: what other modules may depend on
        payments.api.ts     #   interface PaymentsApi + public DTO types
        payments.events.ts  #   event names and payload types
      api/                  # HTTP only
        payments.routes.ts
        payments.controller.ts
        payments.dto.ts     #   Zod request/response schemas and inferred types
      application/          # Use cases / services (business workflows, transactions)
        payments.service.ts
      domain/               # Pure business rules: entities, state machine, domain errors
        payment.status.ts
      infra/                # Persistence and external adapters
        payments.repository.ts
        payments.schema.ts  #   Drizzle tables owned by this module
        payments.outbox.ts
    [other-module]/
  shared/                   # Cross-cutting, domain-agnostic code only
    errors/
    middleware/
    events/                 # Event bus + outbox relay (technical, no domain events defined here)
    context/                # RequestContext type
    utils/
```

Small modules may collapse folders (for example one `payments.service.ts` next to the routes) as long as the public/internal split and the layer direction are kept.

## Layers Inside a Module

Dependencies flow one way: **api → application → domain**, and **application → infra**. The domain layer imports nothing from the other layers.

| Layer | Responsibility | Must NOT |
| --- | --- | --- |
| `api` (routes, controller) | Map HTTP to use cases; validate input (Zod); shape the HTTP response; call the service | Touch the database or hold business rules |
| `application` (service) | Business workflows, authorization checks, transactions, calls to other modules' contracts, emitting events | Know about Express (`req`, `res`) |
| `domain` | Status transitions, invariants, calculations, domain errors | Do I/O, import Drizzle, or import Express |
| `infra` (repository, schema) | All Drizzle queries for this module's tables; external provider adapters | Contain business rules |

### Request context

Services never read `req`. They receive a small context object built once by middleware:

```typescript
// shared/context/request-context.ts
export type RequestContext = {
  userId: string;
  requestId: string;
  // add tenantId, roles, etc. here when needed
};
```

### Example

```typescript
// api/payments.controller.ts
export const makePaymentsController = (service: PaymentsService) => ({
  create: (async (req, res) => {
    const input = req.body as CreatePaymentInput; // already parsed by validate()
    const payment = await service.create(getContext(req), input);
    res.status(201).json({ data: toPaymentResponse(payment) });
  }) satisfies RequestHandler,
});

// application/payments.service.ts
export const makePaymentsService = (deps: { repo: PaymentsRepository; db: Db }) => ({
  async create(ctx: RequestContext, input: CreatePaymentInput) {
    return deps.db.transaction(async (tx) => {
      const payment = await deps.repo.insert(tx, { ...input, userId: ctx.userId });
      await deps.repo.addOutboxEvent(tx, "payment.created", { paymentId: payment.id, userId: ctx.userId });
      return payment;
    });
  },
});
```

Express 5 forwards rejected promises from async handlers to the error middleware automatically. Do not add `try/catch` just to call `next(err)`.

## Module Public API

A module publishes a **contract**, an interface plus types, and `index.ts` exports only that and the wiring function.

```typescript
// contracts/payments.api.ts
export type PaymentView = { id: string; amount: number; currency: string; status: PaymentStatus };

export interface PaymentsApi {
  getPayment(ctx: RequestContext, id: string): Promise<PaymentView>;
  getSummaryForUser(ctx: RequestContext, range: DateRange): Promise<PaymentSummary>;
}
```

```typescript
// modules/payments/index.ts
export { createPaymentsModule } from "./payments.module";
export type { PaymentsApi, PaymentView } from "./contracts/payments.api";
export type { PaymentsEvents } from "./contracts/payments.events";
```

```typescript
// payments.module.ts
export const createPaymentsModule = (deps: { db: Db; events: EventBus; ledger: LedgerApi }) => {
  const repo = makePaymentsRepository();
  const service = makePaymentsService({ repo, db: deps.db, ledger: deps.ledger });
  return {
    api: service satisfies PaymentsApi,                 // for other modules
    router: makePaymentsRouter(makePaymentsController(service)), // for app.ts
  };
};
```

```typescript
// app.ts (composition root, the only place that knows every module)
const ledger = createLedgerModule({ db, events });
const payments = createPaymentsModule({ db, events, ledger: ledger.api });
app.use("/api/v1/payments", payments.router);
```

Rules for the public contract:

- Export **interfaces and plain data types**, never repositories, Drizzle tables, controllers, or domain entities.
- Return plain DTOs (`PaymentView`), not Drizzle rows or classes. This also keeps the contract serializable, which makes extraction to a service possible later.
- A consuming module depends on `PaymentsApi` (the interface), so it can be tested with a fake and later swapped for an HTTP client.
- Changing a contract is a breaking change for consumers. Prefer adding over modifying.

## Rules

1. **Import only through `index.ts`.** Code outside a module may import `@/modules/payments` but never `@/modules/payments/infra/payments.repository`. Inside a module, use relative imports.
2. **No cross-module table access.** A module's repository queries only tables defined in its own `infra/*.schema.ts`. Need data from another module? Call its public contract.
3. **Reference other modules by ID.** Store `paymentId` as a plain column. No cross-module foreign keys and no cross-module joins.
4. **No circular dependencies**, between modules or between files. If A needs B and B needs A, extract the shared concept into a third module, or invert one direction with an event.
5. **Declare allowed dependencies.** Keep the module dependency map (below) up to date. A new arrow needs a review.
6. **`shared/` stays generic.** No domain logic, no imports from `modules/`.
7. **Identity is passed in.** Services receive a `RequestContext`. They never read `req.auth` or `req.body`.
8. **No global singletons for stateful dependencies.** Create them in `app.ts` and pass them down (db, event bus, clients). This makes modules testable and extractable.
9. **Authorization lives in the service/policy layer**, not in controllers and not only in query filters.

### Module dependency map

Maintain this in `docs/modules.md` and keep it acyclic:

```
payments      → ledger (publishes events to), users (reads via UsersApi)
ledger        → (none)
notifications → (consumes events from payments, ledger)
reporting     → payments, ledger (read-only, via query contracts)
```

## Data Ownership

- Every table belongs to exactly one module.
- Use **one Postgres schema per module** so ownership is visible in the database:

```typescript
// infra/payments.schema.ts
import { pgSchema, uuid, integer, text, timestamp } from "drizzle-orm/pg-core";

export const paymentsSchema = pgSchema("payments");

export const payments = paymentsSchema.table("payments", {
  id: uuid("id").primaryKey().defaultRandom(),
  userId: uuid("user_id").notNull(), // plain column, no FK into another module
  amount: integer("amount").notNull(),
  currency: text("currency").notNull(),
  status: text("status").notNull(),
  createdAt: timestamp("created_at", { withTimezone: true }).notNull().defaultNow(),
});
```

- Each migration touches **one module's schema** and is named with the module prefix (`payments_0007_add_refunds`).
- Optional hardening: a database role per module with grants only on its own schema, so a boundary violation fails at runtime too.
- Cross-module reporting: build a dedicated read model or a query contract exposed by the owning module. Do not join across schemas.

## Cross-Module Communication

### 1. Direct call through a contract (default)

Use when module A needs an answer from module B right now.

```typescript
const summary = await paymentsApi.getSummaryForUser(ctx, range);
```

Keep calls coarse-grained (one call returns what the use case needs) to avoid chatty module APIs and N+1 patterns across boundaries.

### 2. Domain events (side effects)

Use when module A announces that something happened and does not care who reacts (for example "payment completed" triggers a notification and a ledger entry).

```typescript
// contracts/payments.events.ts (public, versioned)
export type PaymentsEvents = {
  "payment.completed.v1": { paymentId: string; userId: string; amount: number; currency: string };
  "payment.refunded.v1": { paymentId: string; userId: string; refundId: string };
};
```

Event rules:

- Names are past tense, namespaced by module, and **versioned** (`.v1`). Breaking a payload means a new version.
- Payloads carry IDs and the minimum data needed, not whole entities.
- Delivery is **at least once**, so every handler must be **idempotent** (record processed event IDs).
- Handlers must not assume ordering across different events.
- A handler lives in the **consuming** module and imports only the producer's public event types.

### Transactional outbox (required for events that must not be lost)

Never emit an event "after commit" from application code. A crash in between loses it. Write the event in the **same transaction** as the state change, then relay it.

```sql
CREATE TABLE payments.outbox (
  id            uuid PRIMARY KEY,
  event_type    text        NOT NULL,
  payload       jsonb       NOT NULL,
  created_at    timestamptz NOT NULL DEFAULT now(),
  published_at  timestamptz
);
```

A relay in `shared/events` polls unpublished rows (use `FOR UPDATE SKIP LOCKED`), dispatches them to the in-process bus, and sets `published_at`. Monitor outbox lag (age of the oldest unpublished row).

Pure in-process notifications that can be safely lost (cache invalidation, metrics) may use the bus directly without the outbox.

## Transactions

- One use case = one database transaction **inside one module**.
- Never open a transaction that writes to two modules' tables.
- Cross-module consistency comes from events and the outbox. When a multi-step flow needs compensation (for example a payment succeeds but the ledger posting fails), model it as an explicit process with compensating actions (saga), and document it.
- Keep transactions short. No network calls to external providers inside an open transaction.

## Errors

- The domain and application layers throw typed errors from `shared/errors` (`NotFoundError`, `ConflictError`, `BusinessRuleError`, ...) or module-specific subclasses with stable codes.
- Modules never build HTTP error responses. One central error handler maps errors to responses (see `docs/api-conventions.md`).
- Across a module contract, errors are part of the contract. Document which errors a contract method can throw.

## Configuration, Logging, Observability

- All env variables are parsed and validated once in `config/env.ts`. Modules receive the config they need through their factory, not by reading `process.env`.
- Structured logs include `requestId` and `module`. Create a child logger per module: `logger.child({ module: "payments" })`.
- Trace cross-module calls and outbox dispatch with OpenTelemetry spans.
- Each module may register its own health checks (readiness) and background jobs through its module object. `app.ts` starts and stops them.
- Graceful shutdown: stop accepting requests, drain in-flight work, stop the outbox relay, close the DB pool.

## Enforce Boundaries in CI

Use several layers, since each catches different mistakes.

**1. ESLint: block deep imports through the alias**

```js
// eslint.config.mjs (excerpt)
{
  rules: {
    "no-restricted-imports": ["error", {
      patterns: [{
        group: ["@/modules/*/*"],
        message: "Import from a module's index.ts only.",
      }],
    }],
  },
}
```

**2. dependency-cruiser: catches relative-path violations, cycles, and layer breaks**

```js
// .dependency-cruiser.cjs (excerpt)
module.exports = {
  forbidden: [
    {
      name: "no-deep-module-imports",
      severity: "error",
      from: { path: "^src/modules/([^/]+)/" },
      to: {
        path: "^src/modules/([^/]+)/.+",
        pathNot: ["^src/modules/$1/", "^src/modules/[^/]+/index\\.ts$"],
      },
    },
    { name: "no-circular", severity: "error", from: {}, to: { circular: true } },
    {
      name: "shared-has-no-module-deps",
      severity: "error",
      from: { path: "^src/shared/" },
      to: { path: "^src/modules/" },
    },
    {
      name: "domain-is-pure",
      severity: "error",
      from: { path: "^src/modules/[^/]+/domain/" },
      to: { path: ["/infra/", "/api/", "drizzle-orm", "express"] },
    },
    {
      name: "controllers-do-not-touch-db",
      severity: "error",
      from: { path: "/api/" },
      to: { path: ["/infra/", "^src/db/"] },
    },
  ],
};
```

**3. Architecture tests** for rules tooling cannot express: the module dependency map matches `docs/modules.md`, and no schema file is imported outside its module.

Run all of the above in CI and block merges on failure.

## Testing Strategy

| Level | What | How |
| --- | --- | --- |
| Domain unit tests | State machines, invariants, calculations | Plain functions, no I/O |
| Module integration tests | A module through its public contract | Real Postgres (for example Testcontainers); other modules faked via their interfaces |
| API tests | Status codes, response shapes, error codes, validation | HTTP against the composed app |
| Event tests | Outbox row written in the same transaction; handlers idempotent on duplicate delivery | Integration |
| Architecture tests | Boundary and dependency rules | dependency-cruiser + custom tests |

Because modules receive dependencies through factories, tests construct a module with fakes instead of mocking imports.

## Choosing Module Boundaries

- Split by **business capability and data ownership**, not by technical layer or entity (avoid a `users` module that everything reaches into, and avoid one module per table).
- Signs a boundary is wrong: constant two-way calls, two modules always changed together, a module needing another's tables to do its job.
- Start with fewer, coarser modules. Splitting later is cheaper than merging badly cut ones.
- A module is a good extraction candidate when it has an independent scaling need, a separate team, or a different release cadence. Extraction replaces the in-process contract with an HTTP/queue client and keeps the same interface.
- Record significant decisions (new module, new dependency arrow, boundary exceptions) as short ADRs in `docs/adr/`.

## Creating a New Module: Checklist

1. Create `src/modules/<name>/` with the structure above
2. Define its tables in `infra/<name>.schema.ts` inside its own Postgres schema (see `docs/database.md`)
3. Define the public contract in `contracts/` (API interface and events)
4. Implement `<name>.module.ts` as a factory that receives its dependencies
5. Export only the contract types and the factory from `index.ts`
6. Wire it in `app.ts` and mount its router under `/api/v1/<name>`
7. Add it and its allowed dependencies to the module dependency map
8. Generate and review a migration (touches only this module's schema)
9. Add boundary rules if it needs special handling, and run lint and dependency checks
10. Add domain, module integration, and API tests

## Anti-Patterns

- Importing another module's repository, schema, or internals "just this once"
- Joining across module schemas, or adding a cross-module foreign key
- Returning Drizzle rows or domain entities from a public contract or an HTTP response
- Business logic in controllers or repositories
- Emitting events after commit instead of using the outbox
- Opening one transaction across two modules
- A shared `utils.ts` or `common` module that many modules depend on (it becomes a hidden dependency hub)
- Dumping unrelated helpers or domain concepts into `shared/`
- Global singletons for db, event bus, or other modules (import cycles and untestable code)
- Event handlers that are not idempotent
- Reading `req.auth` or `req.body` inside a service
- A "god" module that coordinates everyone by calling everyone
