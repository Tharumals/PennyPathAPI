# Architecture Guidelines

This project is a **modular monolith**: one deployable Node.js application, split internally into isolated domain modules. Each module owns its data and exposes a small public interface.

**Read this file before:** creating a module, calling one module from another, or changing the project structure.

## Why this architecture

- One deployment and one database keep operations simple
- Strict module boundaries keep the code easy to reason about
- Any module can later be extracted into a separate service with minimal changes

These benefits only hold if the boundaries are respected. Treat a boundary violation as a bug.

## Project Structure

```
src/
  app.ts                  # Express app: middleware, route mounting, error handler
  server.ts               # Entry point (starts the HTTP server)
  config/
    env.ts                # Parses and validates environment variables
  db/
    index.ts              # Drizzle client (see docs/database.md)
    migrations/           # Generated by drizzle-kit, never hand-edited
  modules/
    payments/
      index.ts            # PUBLIC API: the only file other modules may import
      payments.routes.ts
      payments.controller.ts
      payments.service.ts
      payments.repository.ts
      payments.schema.ts  # Drizzle tables owned by this module
      payments.dto.ts     # Zod schemas and inferred types
    [other-module]/
  shared/                 # Cross-cutting, domain-agnostic code only
    errors/
    middleware/
    events/
    utils/
```

## Layers Inside a Module

Dependencies flow one way: **routes → controller → service → repository**.

| Layer | Responsibility | Must NOT |
| --- | --- | --- |
| Routes | Map HTTP paths and methods to controller functions | Contain logic |
| Controller | Parse and validate input (Zod), call the service, shape the HTTP response | Touch the database or hold business rules |
| Service | Business logic, ownership checks, status transitions, transactions, calls to other modules | Know about Express (`req`, `res`) |
| Repository | All Drizzle queries for this module's tables | Contain business rules |

### Example

```typescript
// payments.controller.ts
export const createPayment: RequestHandler = async (req, res) => {
  const input = createPaymentSchema.parse(req.body);
  const payment = await paymentsService.create(getUserId(req), input);
  res.status(201).json({ data: payment });
};

// payments.service.ts
export const paymentsService = {
  async create(userId: string, input: CreatePaymentInput) {
    // business rules live here
    return paymentsRepository.insert({ ...input, userId });
  },
};
```

## Module Public API

Every module has an `index.ts` that exports only what other modules or `app.ts` need.

```typescript
// modules/payments/index.ts
export { paymentsRouter } from "./payments.routes";
export { paymentsService } from "./payments.service";
export type { Payment, CreatePaymentInput } from "./payments.dto";
```

**Never export** repositories, Drizzle tables, or controllers from `index.ts`.

## Rules

1. **Import only through `index.ts`.** Code outside a module may import `@/modules/payments` but never `@/modules/payments/payments.repository`. Inside a module, use relative imports.
2. **No cross-module table access.** A module's repository may query only the tables its own module defines. Need data from another module? Call that module's public service.
3. **Reference other modules by ID.** Store `paymentId` as a plain column. Avoid cross-module foreign keys and joins unless this document explicitly allows them.
4. **No circular dependencies.** If module A needs B and B needs A, extract the shared concept into a third module, or use an event (below).
5. **`shared/` stays generic.** No domain logic, no imports from `modules/`.
6. **Auth identity is passed in.** Services receive `userId` as a parameter. They never read it from `req`.

## Cross-Module Communication

### 1. Direct call (default)

Use when module A needs an answer from module B right now.

```typescript
import { paymentsService } from "@/modules/payments";

const summary = await paymentsService.getSummaryForUser(userId, range);
```

### 2. In-process events (side effects)

Use when module A should announce something happened without caring who reacts (e.g. "payment completed" triggers a notification).

```typescript
// shared/events: a small typed event bus
events.emit("payment.completed", { paymentId, userId });
```

Keep event payloads small (IDs, not full records) and handlers idempotent.

## Enforce Boundaries with ESLint

Add this rule so violations fail the build:

```js
// eslint.config.mjs (excerpt)
{
  rules: {
    "no-restricted-imports": ["error", {
      patterns: [{
        group: ["@/modules/*/*"],
        message: "Import from a module's index.ts only.",
      }],
    }],
  },
}
```

Optionally add `dependency-cruiser` to detect circular dependencies in CI.

## Creating a New Module: Checklist

1. Create `src/modules/<name>/` with the files listed above
2. Define its tables in `<name>.schema.ts` (see `docs/database.md`)
3. Export only the public surface from `index.ts`
4. Mount its router in `app.ts` under `/api/v1/<name>`
5. Generate and review a migration
6. Confirm no file outside the module imports its internals

## Anti-Patterns

- Importing another module's repository or tables "just this once"
- Putting business logic in controllers or repositories
- Dumping unrelated helpers into `shared/`
- Giving a module a catch-all `utils.ts` that other modules depend on
- Reading `req.auth` or `req.body` inside a service
