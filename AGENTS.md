## Project Overview

This is a payment tracking application API. It allows clients to:

- Record and track payments (incoming and outgoing)
- Manage payment statuses and history
- Query and filter payments for reporting
- Access their own data securely via authenticated requests

**Project Type:** Backend REST API (Node.js)  
**Architecture:** Modular monolith  
**Database:** PostgreSQL (via Neon)  
**ORM:** Drizzle ORM  
**Authentication:** Clerk

## Technology Stack

### Core Technologies

- **Runtime:** Node.js (LTS)
- **Language:** TypeScript (strict mode)
- **HTTP Framework:** Express

## Architecture: Modular Monolith

The application is a single deployable unit split into isolated, domain-focused modules. Each module owns its data and exposes a small public interface.

### Project Structure

```
src/
  app.ts                  # Express app setup, middleware, route mounting
  server.ts               # Entry point
  config/                 # Env parsing and validation
  db/
    index.ts              # Drizzle client
    migrations/           # Generated by drizzle-kit
  modules/
    payments/
      index.ts            # PUBLIC API of the module (only entry point)
      payments.routes.ts
      payments.controller.ts
      payments.service.ts
      payments.repository.ts
      payments.schema.ts  # Drizzle tables owned by this module
      payments.dto.ts     # Zod schemas and DTO types
    [other-module]/
  shared/                 # Cross-cutting code only (errors, logger, middleware, utils)
```

### Module Rules

1. **Layering inside a module:** routes → controller → service → repository. Controllers handle HTTP only, services hold business logic, repositories are the only layer that touches Drizzle.
2. **Public interface only:** other modules may import ONLY from a module's `index.ts`. Never import another module's internal files.
3. **No cross-module table access:** a module must not query tables owned by another module. Call that module's public service instead.
4. **No cross-module foreign key joins in queries** unless documented in `docs/architecture.md`. Reference other modules by ID.
5. **No circular dependencies** between modules. If two modules need each other, extract the shared concept or use an event.
6. **`shared/` stays generic:** no business logic or domain knowledge.
7. Keep modules extractable: assume any module could become a separate service later.

## Coding Standards

### General Principles

1. **Type Safety First**
   - Always use TypeScript with strict mode enabled
   - Avoid `any`; use `unknown` or proper type definitions
   - Infer types from Drizzle schemas and Zod schemas instead of duplicating them

2. **Validation**
   - Validate ALL external input (body, params, query) with Zod at the controller boundary
   - Never pass unvalidated data to services or repositories

3. **File Naming**
   - kebab-case for directories: `payment-methods/`
   - `<module>.<layer>.ts` for module files: `payments.service.ts`
   - kebab-case for other files: `error-handler.ts`

4. **Import Organization**
   - Order: external packages → internal modules (via public `index.ts`) → types
   - Use the `@/` path alias defined in tsconfig.json
   - Avoid circular dependencies

5. **Code Style**
   - 2-space indentation, double quotes, semicolons
   - Prefer `const` over `let`; never `var`
   - Use `async/await`; avoid raw promise chains

### Error Handling

- Throw typed application errors (e.g. `NotFoundError`, `ValidationError`) from services
- Handle them in one central error-handling middleware
- Never leak stack traces or internal details in API responses
- Never log secrets, tokens, or full payment details

### Database & ORM

1. **Drizzle ORM Patterns**
   - Define each module's tables in its own `*.schema.ts`
   - Use the type-safe query builder; export inferred types
   - Use transactions for any multi-step write
   - Only repositories may import the `db` client

2. **Migrations**
   - Generate migrations with `drizzle-kit`
   - Review generated SQL before applying
   - Never edit applied migrations; create a new one

### Authentication & Authorization

1. **Clerk Integration**
   - Apply Clerk middleware globally; protect every route by default
   - Get the user from `getAuth(req)` and use `userId` for data ownership
   - Public routes must be explicitly allow-listed

2. **Authorization**
   - Every query for user data MUST be scoped by `userId`
   - Always verify ownership in the service layer, not just the route
   - Never trust client-supplied user IDs

## Payments & Data Integrity

- **Money is never a float.** Store amounts as integers in the smallest currency unit (e.g. cents) or as `numeric`, and always store the currency code alongside
- **Idempotency:** payment-creating endpoints must support an idempotency key to prevent duplicates
- **Status transitions:** define allowed status transitions in the service layer and reject invalid ones
- **Immutability:** do not hard-delete payment records; use status changes or soft deletes and keep an audit trail
- **Timestamps:** store all timestamps in UTC (`timestamptz`)
- **Sensitive data:** never store full card numbers, CVVs, or raw credentials
